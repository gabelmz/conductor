## 3. Bucket assignment (one bucket per report type)

### `update_existing_page`

1. **`kpi_definitions`** → **KPI Studio**
   - Today `frontend/kpi-catalog.js` is a *hardcoded* `Object.freeze` catalog
     (the canonical wording), rendered by `kpi-studio.js`; `reporting/team_kpis.py`
     already has `POST /api/asana/kpis/definitions/import` + `GET /definitions`
     (persists to `asana_kpi_definitions`). The preset should feed Sheet13.csv
     through that import path and let KPI Studio render the imported (not frozen)
     catalog. Update = wire preset detection → `/definitions/import` → KPI Studio.

2. **`catalog_ops`** → **People** (+ **Bulk Import**)
   - `people.py` already stores arbitrary keys in an `attributes` JSON column
     (`KNOWN_FIELDS` = name/role/email/team/notes), so every roster column
     (salary, segment, tenure…) is preserved. Gap: roster is `.xlsx` sheet `BASE`
     with header at row 3; `bulkimport.py`/`bulkimport.js` handle CSV/JSON/NDJSON
     today. Update = add xlsx + sheet + header-row handling and map roster columns
     to `people` (People view already links "Bulk-load a roster from Bulk Import").

3. **`cdq_report`** → **Reports / CDQ**
   - `renderCdqReport` (app.js:3823) already renders CDQ grades, component bars,
     action plan, top fixes, findings — but for the *generated* shape produced by
     `reports.py:generate_cdq()` (computed from local `products`+`checks`), not for
     an uploaded `CDQ_Report.csv`. The preset's per-ASIN fields (cdq_v3_grade,
     title_quality_score, image_quality_score, has_aplus, variations_score…) are
     richer. Update = add a file-ingested per-ASIN table renderer to the Reports
     view and persist the detected file as a report under the shared envelope
     (`reports.py` currently rejects any `kind != "cdq"` in `_generate_report`,
     reports.py:521-522).

4. **`amazon_listings`** → **Listings**
   - `renderListings` (app.js:9033) already has a tabbed shell (Live Listings /
     Suggested vs Live / Glossary). `renderLiveListings` reads the local product
     catalog, not an Amazon listings export. The preset (item_name, price,
     quantity, fulfillment_channel, ASIN) is a Seller-Central listings dump.
     Update = add an "Amazon Listings" tab/source to the Listings view, ingesting
     via `reporting/listing_content.py` (`/api/listings/live/upsert` already
     accepts normalized listing records).

### `needs_new_page`

5. **`asin_map`** → no dedicated vendor→ASIN→SKU view exists.
   - `mapping.js` is *header/schema* reconciliation (different meaning of
     "mapping"); `asin_sources.py` resolves ASIN *sources*, not a vendor→ASIN→SKU
     table; the Product Registry (`productpipeline.py`) tracks items/lifecycle, not
     this raw map. Closest generic home is Data Management (`data.py` routing-table
     source), but the entity deserves a first-class **ASIN/SKU Map** table view.

6. **`reviews_ops`** → no reviews/OPS-sales view exists.
   - `insights.py` is generic profiling (no reviews semantics). Build a
     **Reviews + OPS** view (rating/review count/OPS dollars/refund per ASIN).

7. **`handover_doc`** → no document viewer exists.
   - `renderSops` (app.js:1562) handles *structured* SOP records; `chat.py` `/api/chat/docs`
     uses documents for RAG, not viewing. A DOCX/PDF narrative has no render target.
     Build a **Document viewer** (preset already flags `is_document: true`, fields `[]`).

8. **`sales_by_collection`** → no sales rollup view exists.
   - Dashboard (`renderDashboard`) shows Asana KPI metrics, not sales-by-collection
     with vs-prior-quarter/year deltas. `insights.py` can auto-chart it generically
     as a fallback, but the quarterly rollup needs a **Sales by Collection** view.

### `exists_here_but_broken`

9. **`shipments`** → **FBA view is a stub.**
   - `NAV_ITEMS.fba` (sidebar.js:53) → `view:"fba"` → `VIEW_RENDERERS.fba`
     (app.js:189) → `renderModuleStub("fba")` (app.js:8168) which renders
     "Module scoped — not yet built." The FBA slot exists and is wired but renders
     a placeholder. The preset is "FBA Shipments (Shipment-level)" — exactly the
     FBA domain. Build out the FBA view to render shipments.

### `exists_already_here`

None. No preset is served end-to-end today (detection is brand new and the
file→view routing is unbuilt). The closest is `cdq_report` (a generated CDQ form
is already rendered by the Reports view), which is why it is bucketed under
`update_existing_page` rather than `needs_new_page`.

## 4. Cross-cutting notes

- **Shared report envelope**: the review deferred persisting analytical outputs
  and required `schemaVersion/type/source/parameters/summary`. Any preset whose
  detected file is to be persisted as a report must go through the
  `reports.py` envelope; `_generate_report` (reports.py:520) currently hard-codes
  `kind == "cdq"`, so non-CDQ presets need either envelope extension or their own
  entity store (people/listings already have their own tables).
- **Detection fallthrough**: `detect_report_format` returns `match_type:"none"` for
  unrecognized files → route to the **Mapping** view (`mapping.js`), per
  report_presets.py:400.
- **Generic absorb options** (if dedicated pages are deferred): Data Management
  (`/api/data/table`) and Insights (`/api/insights/upload`) can each render any of
  `asin_map`, `reviews_ops`, `shipments`, `sales_by_collection` as generic tables /
  auto-profiled datasets, but neither gives them catalog-domain semantics.
